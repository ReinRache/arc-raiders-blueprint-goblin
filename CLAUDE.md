# Arc Raiders Blueprint Companion App

## Project Overview
Desktop hobby app (CustomTkinter) that helps *Arc Raiders* players track which crafting blueprints they own, and eventually share "wants/haves" with Steam friends via a cloud DB. Independent project — not part of `python-mech-sim`, separate git repo and venv.

## UI Layout
- The real layout (`src/arc_companion/ui/`) follows `mockup/gemini_mockup.py`, a Gemini-generated mockup the user built as a reference. Treat it as a layout/visual reference only, not working code to copy verbatim — its state semantics (Unowned/Owned/Want/Have) and counting logic have been cleaned up to match the real app's, but it's still just a standalone reference script, not imported by anything.
- `sidebar.py` nav is now just two buttons plus the friends list — **"Manage Friends"** (`btn_manage_friends`, opens `ManageFriendsDialog`) and **"Settings"** (`btn_settings`, opens the new minimal `SettingsDialog`); see "Sidebar & Dialog Reorganization (Stage C follow-up)" below. There's no "My Blueprints" nav item or owned-count label anymore — the app has exactly one view, and the count moved into the main headline. `action_bar.py`'s scan button is also live (renamed "Scan Collection Screenshots" per the designer, opens `ScanDialog`); see "Vision / Screenshot Import (Phase 2)" below.
- The action bar's status label now says "Storage: Local + Cloud (Supabase)" — updated once Phase 3 Stage B added a real cloud store; see "Cloud Sync (Phase 3 Stage B)" below. `ActionBar.set_sync_status(text, color)` updates it further to reflect in-flight/synced/failed states.
- **"Sync Changes" button and dirty-tracking**: wired up per the kickoff doc's own "Client-Side Caching" guardrail (minimize remote API/DB request spam). `MainWindow.dirty` flips `True` after any local status change and calls `action_bar.set_dirty(True)`, which enables the button and lights it up (`#1F6AA5`, matches the theme's active blue); clicking it calls `MainWindow._on_sync_clicked`, which now does a real push to Supabase (see "Cloud Sync" below) and only clears the flag on success. Local `config.json` writes still happen on every click regardless — that's cheap durability, a separate concern from the remote push.
- **Card grid is responsive, not fixed at 10 columns**: `blueprint_grid.py`'s `BlueprintCard` is a fixed logical size (`_CARD_WIDTH`/`_CARD_HEIGHT`, aiming square); `BlueprintGrid.compute_columns()` divides the scrollable frame's *actual* viewport width by that card size to decide how many columns fit, capped at `_MAX_COLUMNS = 10`, and re-renders only when the column count changes. Getting this right requires reversing CTk's DPI-driven widget scaling: on-screen pixel measurements are real physical pixels, but `_CARD_WIDTH` etc. are pre-scaling logical units CTk multiplies internally — use `self._reverse_widget_scaling(...)` (inherited from `ScalingBaseClass`) to get back to the same unit system before comparing, or the column count will be wrong on any display that isn't 100% scaling. Default window (1920x1080, 220px sidebar) computes to the full 10 columns. `_CARD_HEIGHT` grew from 145→172 in Stage C to fit the new friends-overlay row (icon + 4 status dots) below the status button — confirmed via direct `winfo_height()` measurement to match the constant exactly (this only affects vertical scrolling within the grid, not any width-derived window-sizing constant, since `CELL_SIZE`/`_GRID_OVERHEAD_PX` are width-only).
- **`Sidebar` locks its own width with `width=SIDEBAR_WIDTH` + `grid_propagate(False)`, the same technique `BlueprintCard` already uses against its own children — this isn't decorative, it fixed a real regression.** Adding `FriendsSection` (Stage C) silently grew the default window from 10 columns to 9: its `CTkScrollableFrame` has its own natural width (measured at 223px) wider than the sidebar's intended 220px, and without an explicit lock, Tk's grid manager sized the sidebar *column* to fit that content instead of the other way around, stealing width from the grid within the app's fixed total window width. `sidebar.py`'s public `SIDEBAR_WIDTH` constant is now the single source of truth — `main_window.py` imports it for its column's `minsize` and for `_GRID_OVERHEAD_PX` rather than duplicating the literal, so the two can't drift apart again. Confirmed via direct `winfo_width()` that the sidebar stays exactly 220px regardless of friend-list content, and that both the default (10 columns) and minimum (4 columns) window widths compute correctly again.
- **`CTkScrollableFrame` internals gotcha — bind resize handlers to the canvas, not `self`, and always with `add="+"`.** `BlueprintGrid` (a `CTkScrollableFrame`) is itself the *inner content frame*, which customtkinter places inside a real `tkinter.Canvas` (`self._parent_canvas`, the actual scrollable viewport) via `canvas.create_window(...)`, and stretches to match the canvas's width on resize. Two bugs came from getting this backwards:
  1. Binding the column-recompute handler to `self` reads *our own* width, which is a result of the canvas's size, not a measurement of available space — this caused the grid to under-count columns (chunking down early, wasted space on the right), because our own last-rendered width fed back into the next computation instead of the real viewport width. Fixed by binding to `self._parent_canvas` and reading its width instead.
  2. `CTkScrollableFrame.__init__` already does `self.bind("<Configure>", ...)` internally to keep the canvas's `scrollregion` in sync with content size (that's what makes the scrollbar/mouse wheel work at all). A plain `self.bind("<Configure>", handler)` call *replaces* that binding rather than adding to it, silently breaking scrolling — the scrollbar had nothing valid to scroll against and blueprints below the fold became unreachable. Any future `<Configure>`/event binding added to `self` (not just the canvas) must pass `add="+"`.
- **Don't render before the canvas has its real size.** `CTkScrollableFrame` defaults to a 200px-wide canvas until real window geometry settles (we never pass an explicit `width=`/`height=`), so calling `render()` synchronously in `__init__` would lay out cards into that 200px placeholder. `self.columns` starts at `0` — a sentinel `compute_columns()` can never return — so the first real `<Configure>` event is guaranteed to see a "changed" column count and trigger the first render into the *true* canvas size, instead of rendering eagerly into a placeholder.
- **Cards are positioned with `place()`, not `grid()` — this was a real, empirically-confirmed Tk bug, not a style choice.** Originally cards were `grid()`-ed into columns (matching the mockup). That works for the very first render, but once the column count changes on resize (fewer/more columns), re-gridding the *same* card widgets left every column — and therefore every card — a fixed handful of pixels narrower than `_CARD_WIDTH` (e.g. 132px instead of 140px), confirmed by direct `winfo_width()`/`grid_bbox()` inspection outside the full app: Tk's grid geometry manager doesn't cleanly release a weight=0 column's width once the widget that drove it is `grid_forget()`'d and the column count shrinks. This produced the "extra padding on the right, drops a column too early" bug. The only fix that kept `grid()` was destroying and recreating every card on each column-count change, which "fixed" the geometry but was unusably slow (~1s per resize step, a visible hitch, even with icons cached separately — see below). Switching to `place()` with manually computed `x`/`y` pixel coordinates removes the column-width negotiation entirely (nothing to go stale), dropped a full rebuild to ~130ms, and existing cards can just be repositioned instead of recreated. Two `place()`-specific gotchas hit while making this change:
  1. `CTkBaseClass.place()` raises if you pass `width=`/`height=` — those must be set once at construction (`width=_CARD_WIDTH, height=_CARD_HEIGHT` + `grid_propagate(False)`, which is unrelated to and still needed to lock the card's own internal layout); `place()` calls only pass `x=`/`y=`.
  2. `place()` doesn't grow its parent to fit placed children the way `grid()`/`pack()` do with propagate on, so `render()` explicitly sets this frame's height to the total content height afterward (needed for the canvas's scrollregion, and thus the scrollbar/mouse wheel, to reach every row). `self.configure(height=...)` does **not** do this — `CTkScrollableFrame` overrides `configure()` and routes `height` to resizing the *canvas viewport* (`self._parent_canvas`) instead, matching `_set_dimensions()`. Bypass the override with `tkinter.Frame.configure(self, height=...)`, the same pattern customtkinter's own internals use in a few places (e.g. its bg-color handling) to reach the underlying `tkinter.Frame` beneath the CTk wrapper.
- **Icon cache is layered, not one flat dict** (`BlueprintGrid._raw_icon_cache`/`_tinted_backdrop_cache`/`_status_icon_cache`) — decoding an image from disk (PIL open + `CTkImage` construction) is the expensive part of building a card. Even with the `place()` fix, resize-triggered re-renders are debounced (`_RESIZE_DEBOUNCE_MS = 150`, via `self.after(...)` on the canvas's `<Configure>` handler) so a live window drag — many `<Configure>` events in quick succession — settles to one re-layout instead of one per intermediate width.
- **Blueprint icons render on a status-tinted backdrop, mirroring the in-game panel's own distinct "plate" behind each icon — without needing per-blueprint backdrop art.** Tkinter has no native alpha-blend/overlay primitive, so the tint is composited with PIL *before* wrapping the result in a `CTkImage`, not done as a stacked/transparent widget at render time. `blueprint_grid.py`'s `_load_backdrop()` loads the one real backdrop texture the original wiki scrape already pulled down (`data/images/100px-UI_Blueprint_background.png.webp` — present but unused until this feature), `_tint_backdrop()` blends it toward each `STATUS_COLORS` hex (`_BACKDROP_TINT_STRENGTH = 0.5` — texture stays visible, not a flat color swap), and `_compose_status_icon()` pastes the blueprint's own icon on top, inset by `_ICON_INSET_PX` so a ring of tinted backdrop shows around it. Caching is layered so the shared backdrop is only tinted 4 times total (once per status, reused across all 83 blueprints), not once per blueprint per status — `BlueprintGrid._get_status_icon(blueprint, status)` composes and caches the final `CTkImage` lazily, keyed by `(blueprint_id, status)`. A status change (click-cycling, a scan import, a merge) needs a fresh composited image, not just the status button re-styled — `BlueprintCard.set_status()` now takes the new `icon` as a required second argument and swaps `icon_label`'s image, mirroring how it already re-styles the button. Visually confirmed in a live run, not just via isolated PIL previews.
- Text wrapping on card names also uses real font metrics (`CTkFont.measure()`) rather than a guessed characters-per-line budget or CTkLabel's `wraplength` reflow — both were unreliable (inconsistent hard truncation across cards). See `_wrap_name()`.

## Vision / Screenshot Import (Phase 2)
The in-game Blueprints panel is a scrollable grid that doesn't fit one screenshot, so import is a **two-screenshot submission** (scrolled fully to top, then fully to bottom) via `ScanDialog` (`ui/scan_dialog.py`), a guided two-step `CTkToplevel`. Detection logic lives in `src/arc_companion/vision/`, calibrated against `tests/fixtures/blueprints_panel_{top,bottom}.png` at a 2556x1439 reference resolution and **scaled proportionally to whatever resolution an actual screenshot turns out to be** — see "Multi-Resolution Support" below; a screenshot with an implausible aspect ratio still gets rejected with a clear message, not silently misread.

- **Position formula, not per-scan icon recognition**: the designer confirmed the panel's grid layout is fixed for every player (same blueprint always in the same cell), so `blueprint_id_for_position(row, col) = (row-1)*10 + col` (bounded to 1-83) was verified once via direct icon-to-reference-image comparison — 7+ cells spot-checked against `data/images/*.webp` before trusting it — rather than re-identifying icons by computer vision on every user scan. A scan only ever needs to answer one binary question per known position: is it owned?
- **Ownership signal is a "book" category icon in the cell's bottom-left corner, not the checkmark badge near the top-right.** The checkmark region partly overlaps the panel's semi-transparent background (the blurred game scene behind it), so its brightness varies with whatever happens to be behind that specific cell — validated against a hand-verified 47-item ground truth list (provided by the designer from their real account, not inferred from the "FOUND: X/83" counter) and it produced 3 false positives. The book-icon region sits entirely on the cell's opaque name-label strip, giving a much wider, position-independent brightness gap — 0 false positives/negatives against the same ground truth. See `grid_calibration.py`'s `BOOK_ICON_REL_X/Y` and `OWNED_ICON_BRIGHTNESS_THRESHOLD` for the numbers, and `screenshot_reader.py`'s `_is_owned_icon_present`. If detection accuracy regresses after a game UI change, re-run this same verify-against-real-icons process before trusting a new threshold — don't just eyeball it.
- **Top and bottom screenshots do NOT share one row origin.** Bottom-anchored scrolling doesn't land on a clean multiple of the cell pitch from the top-anchored origin (confirmed empirically, off by ~130px from a naive shared-origin assumption) — `GRID_ORIGIN_Y_TOP` and `GRID_ORIGIN_Y_BOTTOM` are two independently-measured constants.
- **Each screenshot's outer-edge row-slot is unreliable and excluded from reading** (`readable_rows_for_scroll` drops it) — it's clipped by the panel's own header chrome or top-edge rounding. Always covered by the *other* screenshot in a pair instead, so nothing is lost; this is also what makes `validate_pair()`'s cross-check (the designer's original "check the scrollbar position to validate proper submission" idea) meaningful — the one row shared between top and bottom is a fully-reliable row in both, not an edge case in either.
- **Merge policy is upgrade-only by default, with an Expedition-regression prompt.** Arc Raiders has a voluntary progression reset ("going on an Expedition"). A scan showing several previously-`OWNED` blueprints as no longer found isn't necessarily a bad screenshot. Below `EXPEDITION_REGRESSION_THRESHOLD` (5) missing items, `apply_upgrade_only` silently adds newly-found ones and leaves everything else alone. At/above the threshold, `ScanDialog` shows the regression count and lets the user choose `apply_upgrade_only` or `apply_full_reset` (treats the scan as authoritative) — never silently downgrades either way. `HAVE` blueprints are never touched by either merge path in either direction — a spare copy isn't something the panel screen can confirm or deny.
- No text OCR (reading the "FOUND: X/83" counter) — would need a new `pytesseract`/Tesseract dependency; scrollbar-pin + shared-row cross-checking covers the same "is this a good submission" question without it. Revisit if that proves insufficient in practice.
- **Deferred, not yet built**: a manual "Reset Collection" action — belongs in the new minimal `SettingsDialog` (general app utilities), not `ManageFriendsDialog`, since it's about local collection state, not friends — for players who'd rather clear their tracked collection directly after an Expedition than resubmit screenshots.

### Multi-Resolution Support
The designer's kid needed the scanner to work on their own monitor, which isn't the 2556x1439 the reference screenshots happened to be captured at — this generalized the vision module from one hardcoded resolution to any resolution, confirmed against real screenshots rather than assumed.

- **The panel's pixel geometry scales proportionally with render resolution — confirmed empirically, not assumed.** The designer captured real top+bottom screenshot pairs at 1920x1080 and 2560x1440 ("2K", their own monitor's native resolution) and provided precise pixel coordinates (not eyeballed crops) for the scrollable grid's corners at both. Both landed within a few pixels of what a straight linear scale (`actual_dimension / reference_dimension`) from the 2556x1439 reference predicts — well inside the jitter already documented between the original two reference screenshots themselves.
- **`grid_calibration.py` now builds a `GridGeometry`** (a frozen dataclass — origin/pitch/scrollbar/icon-region constants, all scaled) via `geometry_for(width, height)`, computed once per screenshot from its actual dimensions and threaded through the rest of the module, instead of every function reading bare reference-resolution module constants directly. The old hard rejection (`abs(width - EXPECTED_WIDTH) > tolerance`) became `is_plausible_aspect_ratio()` (3% tolerance) — rejects a wildly different aspect ratio (e.g. ultrawide, unverified) without pinning to one exact resolution.
- **A real mistake, caught and corrected before it shipped**: an early manual measurement of the bottom-scroll Y origin at 1920x1080 misread which row it was looking at and wrongly concluded that origin specifically didn't scale proportionally (~331px measured vs. ~218px predicted — looked like a real, large discrepancy). The designer's precise pixel coordinates resolved it cleanly: back-derived from their real corner measurement, the true origin was ~224.8px, close to the formula's prediction all along. Documented here as the reason this module leans on precise designer-provided coordinates over the assistant's own crop/zoom measurements when the two disagree.
- **Pure formula-based scaling wasn't quite precise enough on its own for 1920x1080** — close, but off by enough of a small, per-screenshot pixel offset to misread some cells near a viewport edge. Multi-row delta analysis showed this offset is **constant per screenshot, not a compounding/growing pitch error** — so a single real-border measurement is enough to correct the whole origin; no need to re-derive cell pitch. `screenshot_reader.py:refine_geometry()` probes one safely-interior row (row-slot index 2 for top-scroll, 3 for bottom-scroll — the outer edge rows are too close to clipped panel chrome/"FOUND: X/83" text and give unreliable probe results) 10px into the cell (past the rounded corner, matching the offset the original `_has_border_near` window already used), finds the real border via `_find_nearby_border_y()` (a narrow-peak brightness check — bright at y, notably dimmer 3px above and below — deliberately not "brightest pixel in the window," which was confirmed to latch onto bright in-panel text instead of real borders), and shifts the whole Y origin by the measured delta. Falls back to the unrefined formula value if no border is found. `read_grid()` always calls this; `find_panel()` doesn't need it (passed at both new resolutions without refinement).
- **Validated against real screenshots at both new resolutions**, not just formula agreement: `tests/fixtures/multi_resolution/{1920x1080,2560x1440}/{top,bottom}.png` (designer-captured) plus new tests in `tests/test_screenshot_reader.py` (parametrized over both resolutions) confirming `find_panel`/`is_pinned_top`/`is_pinned_bottom` and, critically, that the merged found-set count exactly matches the in-panel "FOUND: 50/83" counter for both — no itemized hand-verified ground truth exists for these captures (unlike the original 47-item one), since the tracked account had progressed to 50 found items by the time these were taken, so the aggregate count plus `validate_pair().ok` is the correctness bar here. 122/122 tests passing (114 original + 8 new), including the original exact-47-item ground truth unchanged.

## Identity & Steam Linking (Phase 3 Stage A)
Kickoff-doc Phase 3 ("Steam Integration & Cloud Database Sync") originally planned Steam OpenID as the *only* identity mechanism. That was revised mid-planning, per the designer: it forced every user through a real Steam login with no privacy-respecting fallback, and it meant nothing in this phase could be self-tested without a human clicking through a real browser flow. The shipped design instead makes local identity **Steam-independent by default**, with Steam linking as an optional add-on layered on top.

- **Every install generates a local "Goblin ID" on first run** (`identity.generate_arbg_id()` → `GBLN-XXXXX`, 5 characters from a 31-character alphabet that excludes visually-ambiguous characters `0/O`, `1/I/L` since codes get read aloud/pasted in chat) — no prompt, no external service, no consent needed since it isn't tied to any real-world identity. This is `UserState.arbg_user_id`, the primary local identity going forward; `steam_id` is now optional (`str | None`), populated only if/when the user links Steam. There is **no global uniqueness registry yet** (no server exists in this pass) — an accepted, documented scope boundary until Supabase adds a DB unique constraint.
- **Friends are a local roster, not a Steam friend-graph read.** `identity.add_friend()` is a pure function (validates format, rejects self-add, dedupes, never mutates its input list) that appends to `UserState.arbg_friend_user_ids`. Comparing collections against these friends needed cloud sync (shipped in Stage B) — `ManageFriendsDialog` says so directly in its copy so it's not confusing why adding a friend doesn't show their blueprints there (the actual comparison lives in the main grid — see "Friend Overlap" below).
- **`ManageFriendsDialog` (`ui/manage_friends_dialog.py`, originally `SettingsDialog` — renamed and split in the Stage C follow-up, see "Sidebar & Dialog Reorganization" below)**. Sections: Goblin ID + Copy button, Friends (add/remove), Steam Account (optional, consent-gated), Steam Web API Key. Content is parented on `self.body`, a `CTkScrollableFrame` filling the fixed 560x680 window — not on `self` directly. Confirmed via live screenshot that even the Stage A section set alone (714px of content) already exceeds the 668px viewport, so any future section added to this dialog should keep parenting on `self.body`, not `self`, or content will silently clip off the bottom again.
- **Steam linking is OpenID 2.0, not OAuth** (`steam/openid_auth.py`) — confirmed via direct web research against Valve's own docs before building anything (per the designer's explicit ask, not assumed): Steam's newer OAuth is gated behind Valve partner approval for a published game and doesn't apply to a fan tool; OpenID 2.0 (`steamcommunity.com/openid`) is still fully supported with no deprecation timeline and is the only mechanism actually available here. Flow: `build_login_url()` opens the system browser at Steam's login page; a loopback-only (`127.0.0.1:17823`) stdlib `http.server` catches the redirect on a background thread; `verify_openid_response()` re-POSTs the params back to Steam with `openid.mode=check_authentication` (the OpenID anti-forgery check) before trusting the SteamID64 extracted from `claimed_id`. No new dependency — stdlib `http.server`/`webbrowser`/`urllib.parse` plus the already-installed `requests`. `login()` never touches Tk objects directly (runs entirely off the Tk thread); callers hop back via `widget.after(0, ...)` in their own callback.
- **Login is "remembered" — no session/refresh-token logic exists or is needed.** OpenID 2.0's `claimed_id` is a stable public identifier; once verified once, a non-null `steam_id` on disk means "linked," full stop. `ManageFriendsDialog` shows that status on every launch with no browser flow auto-triggered. Re-linking only happens via an explicit "Switch Account" click.
- **Steam Web API keys used the BYOK (bring-your-own-key) pattern at this point in the project, later replaced — see "Steam Web API Proxy" below.** Confirmed against Valve's Steamworks docs at the time: "Web API keys must be stored securely and must not be distributed with a game client." Each user got their own free personal key from `steamcommunity.com/dev/apikey`, stored in `storage/local_credentials.py`'s `LocalCredentials` dataclass, persisted to its own `credentials.json`. The key wasn't called anywhere yet in this pass (that's the Steam-friends-lookup feature, which needed cloud sync to be useful) — Stage A just gave users somewhere to put it. `storage/local_credentials.py` and `credentials.json` no longer exist — BYOK turned out to require a phone-verified, non-"limited" Steam account, a real adoption blocker, so the key moved server-side behind a shared proxy instead.
- **Legacy `config.json` migration, not a reset.** Older files predate `arbg_user_id` entirely and used `steam_id: "local_user"` as a placeholder for "no real Steam account." `LocalJSONStore.load_state()` detects both the missing-field case and the placeholder case, assigns a fresh `arbg_user_id`, nulls out the placeholder `steam_id` (a real linked `steam_id` is preserved if present), and leaves `blueprints_owned`/`blueprints_wanted`/`blueprints_spare` untouched either way — see `tests/test_local_store.py`'s two migration tests for both scenarios. The old `LOCAL_USER_ID` constant and `load_state(user_id=...)` selector parameter are gone; there's exactly one local user per machine/file now, so a "does steam_id match" selector no longer applies.
- **What Stage A deferred, and where it landed**: the actual cloud store, `_on_sync_clicked` doing a real push, wiring up "Wipe Cloud Data", and global `arbg_user_id` uniqueness enforcement (a side effect of the `profiles` table's `unique` constraint) all shipped in Stage B. Looking up a friend's collection and showing it against your own shipped in Stage C. Steam persona-name resolution and Steam `GetFriendList` auto-discovery shipped in Stage D.

## Cloud Sync (Phase 3 Stage B)
Backed by a real Supabase project (`arc-raiders-blueprint-goblin`) using **anonymous auth**, not a custom write-token scheme — decided after confirming via Supabase's Python API reference that `set_session()`/`refresh_session()` give the same "remembered login" shape already built for Steam OpenID in Stage A, just without ever needing a browser (anonymous sign-in is a plain API call, so this piece — unlike Steam linking — was fully self-testable end-to-end against the real project, not just mocked).

- **Schema**: `supabase/schema.sql` (checked into the repo as the source of truth, applied by hand in the Supabase SQL Editor — no CI auto-deploy since GitHub integration was skipped when the project was created). One `profiles` row per anonymous-auth user: `id` (references `auth.users`), `arbg_user_id` (now enforced `unique` at the DB level — real global uniqueness, unlike Stage A's locally-generated-only guarantee), `steam_id`, and the three `blueprints_*` integer arrays mirroring `UserState`.
- **RLS**: `select` is public (`using (true)`) — a friend needs to look up your row by Goblin ID without any prior relationship existing, and there's no practical way to restrict that without much heavier machinery (real relational auth, an Edge Function). `insert`/`update` are restricted to `auth.uid() = id`. No `delete` policy/grant on purpose — "Delete My Data" (`cloud/sync.py:wipe_cloud_data`, UI label renamed from "Wipe Cloud Data" in the Stage C follow-up) clears the array columns via `update`, it doesn't drop the row (a friend's lookup shouldn't start erroring for someone who deleted their cloud data). Explicit `grant`s are required in the SQL because "Automatically expose new tables" was deliberately left off when the project was created — RLS alone doesn't make the Data API serve a table.
- **Public-read tradeoff, confirmed with the designer**: since RLS allows anyone with a Goblin ID or SteamID to read that profile row, a linked SteamID64 becomes discoverable that way. Checked rather than assumed: SteamID64 is public-by-design (it's what a Steam profile URL contains), can't be used to access an account (no credentials involved), and is already exposed by countless third-party sites — same risk class as any public username, not account compromise. Same model as a friend-code system (e.g. Nintendo friend codes).
- **The publishable key is committed, not a secret**: `cloud/client.py`'s `SUPABASE_URL`/`SUPABASE_PUBLISHABLE_KEY` constants use the new `sb_publishable_...` key format (confirmed via Supabase's docs that this is *designed* to ship in client code — RLS is the real access boundary) rather than the legacy JWT-format anon key, which is being phased out by Supabase during 2026. This is the opposite treatment from the Steam Web API key (`credentials.json`, BYOK, gitignored) — Valve's docs explicitly forbid shipping that one with a client, Supabase's docs say the reverse for this key.
- **Session persistence**: `storage/supabase_session.py`'s `SupabaseSessionStore` persists `access_token`/`refresh_token` to `supabase_session.json` (gitignored, per-install, distinct from `UserState`/`config.json` which *does* sync). `cloud/sync.py`'s `ensure_session()` restores a saved session via `set_session()` (which auto-refreshes if expired) or falls back to a fresh `sign_in_anonymously()` if none exists or restoration fails (e.g. a revoked refresh token) — treated the same as a fresh install rather than surfacing an unactionable error. **Only ever called lazily from an explicit user action** (clicking Sync or Wipe), never on app startup, so launching the app stays offline-friendly.
- **Background-thread pattern reused from Steam OpenID**: `MainWindow._on_sync_clicked` and `SettingsDialog._on_delete_data_clicked` (the new minimal `SettingsDialog` — see "Sidebar & Dialog Reorganization" below; this lived on the old combined dialog as `_on_wipe_clicked` until the Stage C follow-up) both run their network calls (`ensure_session` + `push_profile`/`wipe_cloud_data`) on a daemon thread and hop back to the Tk thread via `self.after(0, ...)`, mirroring `steam/openid_auth.py`'s `login()` — keeps the UI responsive on a slow/failed connection instead of freezing the mainloop. `_on_sync_clicked` snapshots `UserState` via `dataclasses.replace()` on the Tk thread *before* spawning the worker, rather than reading `self.user_state` from the background thread, so a card click mid-sync can't push a half-old/half-new state.
- **"Delete My Data"** (labeled "Wipe Cloud Data" until the Stage C follow-up) shows a `tkinter.messagebox.askyesno` confirmation (stdlib, no new dependency) making clear it only clears the cloud copy, not local data, before running.
- **Known limitation, accepted rather than solved**: if a user wipes local app data or reinstalls, they lose `supabase_session.json` and their old cloud row becomes orphaned (no recovery — anonymous auth has no email/password behind it). Also worth knowing: Supabase free-tier projects auto-pause after a week of inactivity, which would make Sync/Wipe fail until manually resumed from the dashboard.
- **Verified live against the real project** (not just mocked): anonymous sign-in, session persistence across a simulated relaunch, a real row push + read-back, RLS correctly allowing a second anonymous user to read the row but not write to it, and wipe clearing only the array columns. `tests/test_cloud_sync.py` covers the same logic offline against a fake client for the committed test suite.
- **What this unlocked**: reading a friend's row is what Stage C's friend-overlap grid runs on — see "Friend Overlap (Phase 3 Stage C)" below.

## Friend Overlap (Phase 3 Stage C)
Originally planned as a modest "trade opportunities" dialog. The designer's actual scope was much bigger: **this is the app's main view now, not a separate screen** — every blueprint tile always shows, at a glance, what your selected friends' collections look like relative to yours, and trade-opportunity tiles get a colored outline. Three rounds of clarification during planning locked in Goblin-ID-only names (Steam persona resolution deferred), friend data refreshed by piggybacking on "Sync Changes" (no separate "Refresh Friends" control), and — after initial feedback — the friend-selector list living *inside* the existing sidebar rather than a new column, since the app's width must not grow.

- **Friend selection**: `ui/friends_section.py`'s `FriendsSection` lives inside `Sidebar` (`ui/sidebar.py`), filling the space below the static nav rows (`grid_rowconfigure(3, weight=1)`) and scrolling internally via its own `CTkScrollableFrame` once the list is too long to fit — confirmed via direct `bbox`/viewport-height comparison with 30 friends that it actually overflows and scrolls rather than silently clipping (this app has been burned by `CTkScrollableFrame` assumptions before — see the UI Layout section above). "All"/"None" buttons only ever affect currently-visible checkboxes; `FriendsSection._handle_toggle` explicitly preserves the on/off preference of any friend not currently rendered rather than dropping it.
- **Only friends who've actually resolved to a real cloud row show up at all.** `domain/friends.py:visible_friend_ids()` filters the roster down to `arbg_user_id`s present in the local friends cache — a friend who's never synced, a mistyped/invalid Goblin ID, or (in a future pass) an imported Steam friend never given a real Goblin ID, renders nothing here rather than a "not synced yet" placeholder row. `ManageFriendsDialog` remains the place to see/manage the full roster including unconfirmed entries; this list is specifically "who can I currently compare against." (This was a direct designer correction during planning — the original design showed a placeholder row for unresolved friends.)
- **Per-tile overlay**: `BlueprintCard` (`ui/blueprint_grid.py`) grew a friends-icon + 4-dot row (Unowned/Want/Owned/Have) below the existing status button. Each dot's count is the number of *active* (checked) friends in that state for that blueprint; hovering a dot (via the new reusable `ui/tooltip.py` — CTk has no built-in tooltip widget) lists their Goblin IDs. Dots always render, even at zero friends, deliberately keeping every card's height constant regardless of friend count — this grid has hard-won history with layout bugs from inconsistent card sizing (see the `place()`-vs-`grid()` notes above), not worth reopening for this.
- **Trade-opportunity outline**: `domain/friends.py:compute_highlight(my_status, counts) -> Highlight` is a single deterministic rule — *my own* status alone selects the color family (green = "a friend has one I might want," cyan = "I could give mine away"), since a tile has exactly one of my 4 statuses and the families are mutually exclusive. Within a family, "thick" fires on the strong match (`WANT`+friend`HAVE`, or `HAVE`+friend`WANT`), "thin" on the weak one (`UNOWNED`+friend`HAVE`, or `HAVE`+friend`UNOWNED` with no friend `WANT`). `OWNED` never highlights — a kept copy isn't shareable. Heavily unit-tested (`tests/test_friends_domain.py`) since this is where the real correctness risk concentrates, not something to eyeball.
- **Colors are centralized, not duplicated** — `ui/theme.py` is new: `STATUS_COLORS` (moved from `blueprint_grid.py`'s old private `_STATUS_STYLE`) and `HIGHLIGHT_COLORS`, both single sources of truth so a future visual pass can change e.g. the OWNED color once and have it apply to both the status button and the dots. One gotcha hit here: `CTkFrame.configure()` rejects both `None` and `"transparent"` for `border_color` outright (confirmed directly, not assumed) — the `Highlight.NONE` entry uses a real neutral hex instead, which is safe since `border_width=0` means the color is never actually painted regardless of value. Values already tuned once from designer feedback (see below) — `STATUS_COLORS[UNOWNED]` lightened (`#333333`→`#5C5C5C`, the original blended into the icon/card background) and `HIGHLIGHT_COLORS[NONE]` changed from invisible (`border_width=0`) to a visible thin light-grey outline, so neutral tiles still read as tiles.
- **Freshness**: no separate "Refresh Friends" control — `MainWindow._on_sync_clicked`'s worker, after `push_profile` succeeds, also calls `cloud/friends.py:fetch_friend_profiles()` (one batched `.in_()` query, not one per friend) and caches the result via `storage/friends_cache.py`'s `FriendsCacheStore` (`friends_cache.json`, gitignored — fetched data, not the designer's own progress). A friend-fetch failure doesn't undo a successful push; the overlay just doesn't refresh that time. Reads don't strictly need an authenticated session (Stage B's RLS grants `select` to the `anon` role too), but the sync flow already has one in hand from pushing, so it's reused at no extra cost.
- **"Last synced" label**: `ActionBar` (`ui/action_bar.py`) shows a compact age next to "Sync Changes" (`domain/time_format.py:format_sync_age()` — `<1 min ago` / `X mins ago` / `X hours ago` / `X days ago` / `Never synced`, correct singular/plural). Self-reschedules a `after(30_000, ...)` tick since the bucket a timestamp falls into changes just from time passing, with no user action to hang a refresh off of. `UserState.last_synced_at` (epoch seconds, local-only) is set only on a successful sync — distinct from `updated_at`, which bumps on every local edit.
- **Active-friend reconciliation**: `domain/friends.py:reconcile_active_friends(new_ids, previous_ids, previous_active_ids)` needs *three* inputs, not two — this was a bug caught during implementation (not by review): with only the new roster and the previous active set, "brand new friend" and "existing friend toggled off" are indistinguishable (both look like "not in previous active"). The previous full roster resolves the ambiguity. New friends default active; existing friends keep their prior on/off state; removed friends are dropped.
- **Everything reachable without a browser or human is self-verified**: `tests/test_friends_domain.py`, `tests/test_time_format.py`, `tests/test_friends_cache.py`, `tests/test_cloud_friends.py` (offline, fake client) plus a live run against the real Supabase project — two distinct fake friend profiles pushed under two separate anonymous sessions, fetched by a third unrelated session via the batched query, confirmed exact row matching. Also confirmed end-to-end in-process: friend add/remove → active-set reconciliation → cache pruning → grid overlay refresh, all the way through a real `MainWindow`.
- **Designer visual review — two rounds, both resolved.** Round 1 (colors/labels, see above and "Sidebar & Dialog Reorganization" for the sync-button wording change) confirmed the automated checks alone weren't enough — direct precedent for the general principle that this app's visual polish needs real eyes on it (see the Settings dialog clipping bug in Stage A). Round 2 caught a genuine functional regression, not just polish: the default window silently dropped from 10 columns to 9. Root cause and fix are documented in the "`Sidebar` locks its own width" bullet in the UI Layout section above.
- **Explicitly deferred**: Steam persona-name resolution and `GetFriendList` auto-discovery shipped in Stage D (see below). Still deferred: a standalone manual "Refresh Friends" control, syncing the friends roster or active-selection to the cloud (both stay local-only, same as Stage A's `arbg_friend_user_ids`), and any broader visual/theming pass beyond the colors this feature touches.

## Steam Friends API (Phase 3 Stage D)
**Superseded by "Steam Web API Proxy" below** — the BYOK key (`steam/web_api.py`, `storage/local_credentials.py`, the "Steam Web API Key" section this section describes) was removed entirely once the proxy shipped. Kept here as history/context for *why* the feature is shaped the way it is (batching, the private-friends-list error, the piggyback-on-Sync pattern) — all of that carried over unchanged, only where the key comes from changed.

Ships the two pieces Stage C explicitly deferred: real Steam display names instead of Goblin IDs, and auto-discovering which real-life Steam friends are also using the app.

- **`steam/web_api.py`** is new — distinct from `steam/openid_auth.py`, which only handles sign-in. `get_player_summaries(api_key, steam_ids)` (`GetPlayerSummaries/v2/`, batched 100 per call) and `get_friend_list(api_key, steam_id)` (`GetFriendList/v1/`). Both confirmed directly against Valve's docs before building, not assumed: **`GetFriendList` returns HTTP 401 if the target account's "Friends List" Steam privacy setting isn't public** — a real documented failure mode, raised here as `SteamFriendsListPrivateError` so the UI can show an actionable message instead of a generic failure. Both use `api.steampowered.com` (the standard BYOK-compatible host), not `partner.steam-api.com` — same reasoning Stage A already established for OpenID (unofficial third-party tools use a personal key against the standard endpoints, not the Valve-partner-gated ones).
- **No schema change needed** — `profiles.steam_id` already had an index (`profiles_steam_id_idx`, from Stage B) purpose-built for exactly this: matching a Steam friend's SteamID64 against "is this person also on the app" is `cloud/friends.py:fetch_profiles_by_steam_ids()`, one batched `.in_("steam_id", ...)` query, same shape as the existing `fetch_friend_profiles`.
- **Persona names piggyback on Sync, no new trigger** — consistent with Stage C's "one network action does everything" pattern. `MainWindow._on_sync_clicked`'s worker, after the existing friend-data fetch, makes one batched `get_player_summaries` call covering both the viewer's own `steam_id` (if linked) and every fetched friend's `steam_id` (if any) — entirely skipped if no Web API key is saved. Resolved names land in `UserState.steam_persona_name` (local-only, mirrors `last_synced_at`'s treatment — never in `push_profile`'s payload) and `FriendProfileSnapshot.steam_name` (cached in `friends_cache.json` alongside the rest of that friend's snapshot). `MainWindow._display_name()` and `FriendsSection._display_name_for()` both prefer the resolved name, falling back to the Goblin ID exactly as before Stage D existed. A resolution failure doesn't undo the sync or the friend-data refresh — same tolerance already established for the friend-fetch step itself.
- **"Find Steam Friends"** — new section in `ManageFriendsDialog`, visible/enabled only once Steam is linked *and* a Web API key is saved (checked both at dialog build time and re-checked after linking or saving a key). Click → background thread (same threading + `after(0, ...)` pattern as every other network action in this app) runs `get_friend_list` → `fetch_profiles_by_steam_ids` → `domain/friends.py:discoverable_steam_friends()` (drops candidates already in the roster, orders results to match Steam's own friend-list order) → resolves display names for the candidates via `get_player_summaries` (best-effort — a failure here just shows Goblin IDs instead of names, doesn't block the list) → a checklist, **unchecked by default** (adding a friend is a more deliberate action than toggling a comparison checkbox, so this opts in rather than out) → "Add Selected" runs each through the existing `identity.add_friend` and the existing `on_friends_changed` callback, so Stage C's reconciliation/cache-pruning wiring in `MainWindow` applies unchanged. `ManageFriendsDialog` gained a `cloud_client` constructor parameter for this (no `cloud_session_store` needed — reads don't require auth, same as Stage C's friend fetch).
- **A real bug, caught by my own in-process testing, not by review**: the discovery worker's `except SteamFriendsListPrivateError as exc:` originally built its `self.after(0, lambda: ...)` callback referencing `exc` directly inside the lambda. Python auto-unbinds an `except ... as name` variable at the end of its except block — since the lambda only actually runs later (asynchronously, once the Tk thread gets around to it), `exc` no longer existed by the time the lambda executed, raising `NameError` instead of showing the intended message. Confirmed by triggering it directly, not just reasoning about it. Fixed by capturing `str(exc)` into a plain local variable before constructing the lambda. Worth remembering as a general pattern: **any exception object referenced inside a deferred `self.after(0, lambda: ...)` callback must be captured to a plain value first**, not closed over directly.
- **Self-tested thoroughly, with one real limitation** — everything except the actual live Steam API calls is self-testable and was tested: `fetch_profiles_by_steam_ids` against the real Supabase project (pushed a real fake friend profile with a known `steam_id` under its own anonymous session, then ran the full discovery flow — with only `get_friend_list`/`get_player_summaries` mocked — against it live, end to end, including selecting and adding the discovered candidate through the real `MainWindow`), plus the private-friends-list error path and the persona-name-updates-the-headline path. What wasn't self-testable: whether the designer's own real Web API key and linked Steam account actually work against Steam's live API — direct parallel to Stage A's Steam OpenID login. **Confirmed working by the designer** with their real account (correctly returned zero results, since their kid isn't registered on the app yet — an empty result is itself proof the live call succeeded, not a failure).

## Steam Web API Proxy (replaces Stage D's BYOK key)
Removes the per-user "bring your own Steam Web API key" requirement entirely. Real blocker, not just friction: Valve requires the linked Steam account to be non-"limited" (spent $5+ in the Steam store) **and have a phone number on file** before it can generate a key at all — the designer's kid doesn't have a phone, so his install could never get one. A Web API key authenticates the *calling application*, not which Steam account's data it's allowed to fetch (the same way any third-party Steam stats site works), so one key — the designer's own, already phone-verified — now serves every user, held server-side, never shipped with the client.

- **First non-Python code in this repo**: two Supabase Edge Functions (Deno/TypeScript), `supabase/functions/steam-player-summaries/index.ts` and `supabase/functions/steam-friend-list/index.ts`, plus a shared `supabase/functions/_shared/steam_proxy_common.ts`. Two functions, not one dispatcher — their request/response shapes and error semantics genuinely differ (only friend-list has the private-list case), mirroring the 1:1 split the old `steam/web_api.py` already had.
- **Auth is free, from Supabase itself**: both functions have `verify_jwt = true` (`supabase/config.toml` — the CLI default, set explicitly here for documentation rather than left implicit). A request with no valid Supabase session bearer token is rejected before either function's code runs at all — meaning every caller is a real anonymous-auth user of this app (from `ensure_session()`), not an anonymous stranger on the internet.
- **Per-user daily call cap, not just the JWT gate** — directly addresses the "attacker drains your quota / gets the key flagged" risk: a new `steam_proxy_usage` table (`supabase/schema.sql`) plus an atomic `increment_steam_proxy_usage(p_user_id)` SQL function (single `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`, not a separate read-then-write, so concurrent calls from the same user can't under-count each other). Both the table and the function are reachable *only* by the `service_role` key (auto-injected into every Edge Function by Supabase, never client-supplied) — no `anon`/`authenticated` grants at all, and the function's own `p_user_id` parameter is caller-supplied rather than derived from `auth.uid()` internally, so exposing it to those roles would let one user grief another's counter. Cap is a flat 200/day, generous relative to real usage (a handful of calls per sync/discovery click) — meant to stop a runaway bug or deliberate abuse, not to meter normal use. Over-cap returns `429` with `{"error": "rate_limited"}`.
- **Every Edge Function error path returns a JSON body with an `"error"` key** — not a style preference, a correctness requirement: confirmed by reading the installed `supabase_functions` Python package (`.venv/Lib/site-packages/supabase_functions/_sync/functions_client.py`) that on any non-2xx response it unconditionally does `response.json().get("error")` — a non-JSON error body would raise a confusing `JSONDecodeError` on the Python side instead of a clean, catchable `FunctionsHttpError`.
- **`src/arc_companion/cloud/steam_proxy.py`** replaces `steam/web_api.py` (deleted), same function names/signatures except taking `client: Client` instead of `api_key: str`, calling `client.functions.invoke(...)` (confirmed `supabase==2.31.0`'s `client.functions` property exists and stays in sync with whatever session `client.auth` currently holds — same ordering requirement as `push_profile`, callers must `ensure_session(...)` first). Catches `FunctionsHttpError` (`.status` = HTTP status, `.message` = the `"error"` body key) and translates `403`/`"friends_list_private"` → `SteamFriendsListPrivateError` (same class/meaning as before, moved into this module) and `429` → new `SteamProxyRateLimitedError` (shown as "Too many requests — try again later" wherever errors already surface to the user).
- **`ManageFriendsDialog` gained a required `cloud_session_store` constructor parameter** it didn't need before — Stage D's discovery flow never needed auth (`fetch_profiles_by_steam_ids` reads under a public RLS `select` policy), but the new proxy calls do (`verify_jwt`), so `_on_discover_clicked`'s worker now calls `ensure_session(self.cloud_client, self.cloud_session_store)` before either proxy call, mirroring `main_window.py`'s sync worker. Wired at the one call site, `main_window.py:_on_manage_friends_clicked`, passing the `SupabaseSessionStore` `MainWindow` already holds for `_on_sync_clicked`.
- **Discovery's gating simplified**: `_refresh_discover_button_state`/`_on_discover_clicked` now check `self.steam_id` alone — no more `and api_key`, since there's no per-user key to check. Anyone with Steam linked can use "Find Steam Friends" and get persona names, regardless of whether their own Steam account could ever generate a Web API key itself.
- **Removed entirely**: `src/arc_companion/steam/web_api.py`, `src/arc_companion/storage/local_credentials.py`, `tests/test_steam_web_api.py`, `tests/test_local_credentials.py`, and the "Steam Web API Key" section (link to `steamcommunity.com/dev/apikey`, the "Domain Name: localhost" note, the key entry field) from `ManageFriendsDialog`. `steam/openid_auth.py` (Steam login/linking) is untouched — that was always separate from the Web API key and has no phone-number requirement of its own.
- **Deployment is manual, designer-run** — same "hand-applied, checked in for history" treatment `schema.sql` already had, extended to a first real Supabase CLI workflow (`supabase/config.toml`'s `project_id` links this repo to the same `arc-raiders-blueprint-goblin` project): `supabase login` → `supabase link --project-ref ysagpirtcslsnbqotwhp` → `supabase secrets set STEAM_WEB_API_KEY=<key>` (the designer's own key, now held server-side instead of locally) → apply the `steam_proxy_usage` table + function via the SQL Editor → `supabase functions deploy steam-player-summaries` and `supabase functions deploy steam-friend-list`. Local Edge Function emulation (`supabase start`, needs Docker — not installed on this machine) is skipped; verified live against the real deployed project instead, matching how Stage B/D were both verified.
- **Deployed and confirmed working live by the designer**: both functions deployed (`ACTIVE`, `verify_jwt: true` confirmed via `supabase functions list`), the `steam_proxy_usage` table + RPC applied by hand in the SQL Editor. Sync resolved the designer's real Steam persona name through the proxy (no locally-saved key involved at all), and Find Steam Friends correctly found and returned their kid's account — the exact scenario that motivated this whole change, since that account could never have gotten its own Web API key. Python side is also covered offline by `tests/test_cloud_steam_proxy.py`, mirroring `test_cloud_friends.py`'s `FakeClient` convention.

## Standalone Build
For sharing a runnable copy with someone who doesn't have Python — first time this app has actually been built with the `pyinstaller` dependency that's sat in `requirements.txt` since Phase 1.

- **Two different kinds of file location needed splitting apart, not just "make paths frozen-aware."** `src/arc_companion/paths.py` is new: `resource_root()` (bundled read-only data — `data/blueprints.csv`, `data/images/`) and `user_data_root()` (writable per-install files — `config.json`, `credentials.json`, `supabase_session.json`, `friends_cache.json`). Both fall back to today's repo-root behavior when not frozen (`getattr(sys, "frozen", False)` is `False`), so `python main.py` from source is unaffected. When frozen: `resource_root()` resolves to PyInstaller's own bundle-location signal (`sys._MEIPASS`); `user_data_root()` resolves to the folder the actual `.exe` sits in (`Path(sys.executable).parent`) — deliberately *not* inside PyInstaller's `_internal/` folder, so a user's saved data is visible and easy to find next to the exe, not buried in bundle internals. This replaced five near-identical `Path(__file__).resolve().parents[3]` blocks (`data/blueprints.py` + all four `storage/*.py` files) with one shared module — a real simplification independent of the packaging goal.
- **`--onedir`, not `--onefile` — confirmed against CustomTkinter's own packaging docs, not assumed.** CTk ships its own data files (`.json` theme files, `.otf` fonts) that PyInstaller doesn't auto-include, and CTk's docs explicitly say onefile mode doesn't work for it. So what gets shared is a **folder** (`dist/ArcRaidersBlueprintGoblin/`, containing `ArcRaidersBlueprintGoblin.exe` + an `_internal/` support directory) — not a single portable file. Worth saying plainly when handing this off, so "I'll send you the exe" doesn't turn into "why won't it start" when only the `.exe` itself gets copied without the folder around it.
- **`arc_companion.spec`** (repo root) is a hand-crafted, committed, reproducible build config — not the auto-generated kind `pyinstaller main.py` would produce on a bare CLI run. Bundles this app's `data/` folder and customtkinter's own package directory (found via `customtkinter.__file__` at build time) via `Analysis(datas=[...])`. `.gitignore`'s blanket `*.spec` rule got a `!arc_companion.spec` exception so this one specific file stays committed while any throwaway auto-generated spec still wouldn't be.
- **Actually built and run, not just coded** — this is the one pass in the project so far where "does it run" could only be answered by producing a real `.exe` and launching *that*, not `python main.py`. Confirmed: the grid renders with real bundled icons (`resource_root()` found the bundled data), `config.json` appears next to the `.exe` with a fresh Goblin ID (`user_data_root()` resolved correctly, not into `_internal/`), and — the one real remaining risk, since PyInstaller can silently break libraries with complex dynamic imports — **the designer confirmed Sync actually works in the built exe** against the real Supabase project (`last_synced_at` populated, `supabase_session.json`/`friends_cache.json` both created correctly).
- Build command: `.venv\Scripts\python.exe -m PyInstaller arc_companion.spec --noconfirm`. A `WARNING: Hidden import "tzdata" not found!` appears during the build — checked rather than ignored: this app's own code never touches `datetime`/`zoneinfo` (grepped to confirm), so it's a transitive notice from somewhere in the Supabase client's dependency chain, not something our own code paths exercise; the actual built-and-run test above didn't surface any resulting failure.
- **Explicitly not done this pass**: code signing (the exe is unsigned — Windows SmartScreen will likely flag it as "unrecognized" on a machine that's never seen it, a known/expected nuisance, not a bug to chase down), an installer, an icon, and the kickoff doc's actual "Phase 5" content (a `version.json` self-update check — unrelated; that's about detecting new releases, this pass just produces the first buildable one).

## Data
- `data/blueprints.csv` and `data/images/` are the real master blueprint list (83 items, sourced from the Arc Raiders Wiki and an existing HTML prototype the user maintained) — not placeholder data. Treat edits to this file as data-entry changes, not code changes.
- Rarity is sourced per-item from `arcraiders.wiki/wiki/<Item_Name>` infobox pages; all 83/83 resolved. Not yet surfaced in the UI (the mockup's cards don't show it either).

## Domain: blueprint status
- `src/arc_companion/domain/status.py` — `BlueprintStatus` (`IntEnum`, ordered UNOWNED/WANT/OWNED/HAVE to mirror how ownership actually progresses — clicking a card's status button cycles via `.next()` in that order, and it's also the left-to-right order of the 4 friend-overlay dots on each card, since `blueprint_grid.py` iterates `enumerate(BlueprintStatus, ...)` directly) plus pure `status_for`/`apply_status` functions, kept out of the UI layer so they're unit-testable without a display. Reordering the enum is safe for persisted data — `UserState`/the cloud `profiles` table store blueprint IDs in three separate `owned`/`wanted`/`spare` id sets, never the enum's raw integer value.
- Semantics (confirmed with the user, since the mockup itself was ambiguous): **Owned** = you secured/kept the blueprint (consumable, one-time use). **Want** = you don't have it and are looking for one. **Have** = you have a spare copy free to give away — and it also counts as "Owned" for collection-percentage accounting, i.e. `HAVE` is a superset of `OWNED` plus a spare flag, not an independent 4th state.

## Persistence
- `src/arc_companion/storage/base.py` defines a `Store` ABC (`load_state`/`save_state`) so the Phase 1 `LocalJSONStore` can be swapped for a Phase 3 Stage B cloud-backed store without changing the data model.
- State shape: `{"arbg_user_id": ..., "steam_id": ..., "arbg_friend_user_ids": [...], "arbg_active_friend_ids": [...], "blueprints_owned": [...], "blueprints_wanted": [...], "blueprints_spare": [...], "updated_at": ..., "last_synced_at": ...}`. `arbg_user_id` is always present (generated on first run — see "Identity & Steam Linking" above); `steam_id` is `null` until Steam is linked; `arbg_active_friend_ids` and `last_synced_at` were added in Stage C (see "Friend Overlap" below) and are both local-only, same treatment as `arbg_friend_user_ids` — none of the three are included in `push_profile`'s payload. Use `blueprints_owned`/`blueprints_wanted`/`blueprints_spare` (not the kickoff doc's shorthand `blueprints`/`wants` names from its intro example — Phase 6 already spells out the real field names, and `blueprints_spare` extends that same pattern for the "extra copy to share" concept).
- `storage/supabase_session.py`'s `SupabaseSessionStore` is a separate, parallel store for `supabase_session.json` (`access_token`/`refresh_token` from anonymous auth) — see "Cloud Sync (Phase 3 Stage B)" below. Distinct from `UserState` (syncs): this is a per-install session token for the app's own backend, not user-facing data and not something that syncs anywhere. (`storage/local_credentials.py`, a similar parallel store for a locally-saved Steam Web API key, existed here until the "Steam Web API Proxy" work removed BYOK entirely — see that section below.)
- `storage/friends_cache.py`'s `FriendsCacheStore` is a fourth separate, parallel store for `friends_cache.json` (a locally-cached copy of each friend's `profiles` row) — see "Friend Overlap (Phase 3 Stage C)" below. Distinct from all three above: this is *fetched cloud data about other people*, not local progress, not a secret, and not a session token — its own category, gitignored like the rest.

## Working Conventions
- Run `python -m pytest` from the repo root to verify tests pass.
- Run `python main.py` to launch the app for manual UI verification — GUI code is not unit-tested (CustomTkinter needs a real display).
- Environment: `venv` + `requirements.txt`/`requirements-dev.txt` (no `pyproject.toml`/build backend — kept intentionally simple for a single-dev hobby app).
- Run `.venv\Scripts\python.exe -m PyInstaller arc_companion.spec --noconfirm` to produce a standalone Windows build in `dist/ArcRaidersBlueprintGoblin/` for sharing with someone who doesn't have Python — see "Standalone Build" below before assuming a code change here is safe; it touches file-path resolution used by every storage module.
- Edge Function changes (`supabase/functions/`) need the Supabase CLI (`npm install -g supabase`) — deploy with `supabase functions deploy <name>` after `supabase login`/`supabase link --project-ref ysagpirtcslsnbqotwhp`. Designer-run, not something to do unprompted — see "Steam Web API Proxy" below for the full sequence and why (touches live account credentials and the real Steam Web API key).
